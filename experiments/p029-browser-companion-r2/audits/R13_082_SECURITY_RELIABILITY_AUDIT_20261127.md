## Критические / высокие дефекты (проверены повторяемыми изолированными тестами)

### A1 · HIGH · Исполнение действия ПОСЛЕ отзыва доступа — RELEASE BLOCKER

- **Код:** `extension/background.js` `performJob` (первичная проверка grant), затем `chrome.tabs.get`, затем ветка `pin_tab` / `chrome.tabs.update` без повторной проверки полномочий непосредственно перед действием.
- **Воспроизведение:** специально задерживаем асинхронный `tabs.get`, нажимаем `disable-full` (локально остаётся 0 grants), затем снимаем задержку. Исходная задача завершается `ok:true` и **закрепляет вкладку после отзыва доступа**.
- **Команда:** `node --test audits/r13_082_audit_repros.test.mjs`. Протокол `AUDIT_REPRO_PAUSE_RACE`.
- **Воздействие:** `pin_tab` — безвредный пример. Такой же класс гонки следует проверять для `navigate`, `close_tab`, `download_url`, изменения окна и операций клавиатуры. Не доказано, что все остальные уязвимы, но общая архитектура допускает окно TOCTOU.
- **Исправление:** номер поколения/epoch разрешений, отмена pending jobs, повторная авторизация прямо перед каждым побочным действием после любого `await`, сериализация ревокаций и применения команд, разграничение «начато до» и «выполнено после». Не добавлять дополнительные popup-подтверждения на каждую команду.

### A2 · HIGH · Экспорт конфиденциального содержимого форм — RELEASE BLOCKER

- **Код:** `extension/extended-dom-ops.js` `get_form_values`: исключаются поля `type=password` и `type=file`, но **читаются `type=hidden` и текстовые поля OTP**. `get_selected_html` клонирует выделенный subtree и отдаёт `innerHTML` **без редактирования value-атрибутов даже в `input[type=password]`**.
- **Воспроизведение:** изолированный Chrome с синтетическими `EXAMPLE_LOCAL_CSRF`, `EXAMPLE_LOCAL_OTP`, `EXAMPLE_LOCAL_PASSWORD`; `get_form_values` экспортирует hidden/OTP; `get_selected_html` возвращает значение парольного `value` из исходного HTML.
- **Доказательство:** `AUDIT_REPRO_FORM_LEAK`, `AUDIT_REPRO_SELECTED_HTML_LEAK` — без чтения настоящих данных пользователя.
- **Исправление:** единая политика редактирования секретов для чтений DOM: не возвращать `value` hidden/OTP/recovery/autocomplete-sensitive fields и исключить атрибуты `value`/токены из сериализованного выделенного HTML; тесты на маскировку, nested forms, shadow DOM. Учесть, что фильтр по одному имени поля не обеспечивает полного предотвращения утечек.

## Надёжность / UX

### A3 · MEDIUM/HIGH · Линейная нагрузка каждые ~5 секунд

- **Код:** `background.js` `poll`→`refreshFullGrants`→`setGrants` + `prune` + повторные публикации.
- **Воспроизведение в VM для 125 вкладок:** за **один poll** 125 `chrome.tabs.get`, 125 `setBadgeText`, 125 `setBadgeBackgroundColor`; **2 POST grants**, **2 POST tab-overview**, **1 GET jobs**. 500 вкладок масштабируют эту схему. Реальные измерения CPU/батареи не проводились.
- **Исправление:** событийные и дельта-обновления, дедупликация по хешу содержимого, ограниченные пакетные записи; отдельный лёгкий опрос jobs. Профилировать CPU/RAM на 100–500 вкладках.

### A4 · MEDIUM · Полный доступ молча возобновляется после перезапуска

- **Код:** `fullMode` сохраняется в `chrome.storage.local`; `poll` создаёт grants при пустой новой `chrome.storage.session`. При сохранённых Chrome-разрешениях вкладки снова становятся управляемыми **без новой кнопки**.
- **Воспроизведение:** VM, `fullMode:true`, grants пустые; один `poll` выдаёт grants всем 3 тестовым вкладкам.
- **Замечание:** такое постоянное автопродолжение может быть предпочтением владельца. Тогда следует прямо указать «доступ сохраняется между перезапусками», а не одновременно писать «browser session ends them». И обеспечить осмысленное выключение без гонки A1.

### A5 · RELEASE ACCEPTANCE GATE · Первичное Chrome-разрешение не подтверждено

- В исходном `manifest.json` используются `optional_permissions` (`tabs,debugger,downloads`) и `optional_host_permissions` (HTTP(S) сайтов). Временно изолированный **headless Opera** при нажатии `Enable full browser control` в обычной установочной конфигурации ответил `Only permissions specified in the manifest may be requested`; повторно проверенный сценарий **с предварительно выданными разрешениями** PASS.
- Это может быть особенность headless/Opera, **не доказанная неисправность Chrome**. Нужна реалистичная штатная установка и один явный owner gesture в Chrome/Opera без обхода системного диалога.
- См. `QA_R13_OWNER_PERMISSION_FLOW_20261127.json` (локально) и `QA_R13_PREAPPROVED_PERMISSION_FLOW_20261127.json` (в репозитории).

### A6 · LOW/MEDIUM · Несовпадение возможностей в разных браузерах

- Установленная Opera Chromium может игнорировать предложенное имя скачанного файла, хотя содержимое скачано правильно.
- `Meta+A` достигал DOM в виде `keydown` с `metaKey=true`, но штатное выделение текста в тестовой headless Opera не подтверждено. Протокол 19/19 должен интерпретироваться как проверка объявленных действий и частичных побочных эффектов, **не 100% семантический паритет клавиатуры/загрузок**.
- `manifest.minimum_chrome_version=116`, тогда как 30-секундные alarms доступны с Chrome 120; требуется поправить матрицу совместимости либо обеспечить fallback для 116–119.

## Границы проверки

- Тесты выполнены на **временных, локальных данных**, без чтения пользовательских вкладок, сообщений, паролей, платёжных страниц и AWS production. Изменения работающих расширений не выполнялись.
- Ни одна из проверок не подтверждает реальную многодневную устойчивость, исполнение 100/100 на production, OAuth/AWS end-to-end, первоначальный диалог Chrome или переносность на Chrome 116.
- **4/4 adversarial audit probes PASS означает: четыре описанных класса дефектов/свойств воспроизведены**; это НЕ значит, что аудит признал выпуск безопасным.
- Автор исходного кода и аудитор находятся в одной сессии ассистента; **отдельная организационно независимая QA/Critic-подпись не получена**.
