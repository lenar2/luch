# R8.4 — independent human usefulness pilot
Status: HEA proposal prepared after R8.3.2 implementation, BEFORE any participant data. Not an independently registered baseline, not a study result, not a release approval.
Frozen product candidate: 4c6c0cdc55b1f7fcbd7aa3e319110d1cc528a44a (product files must not change during this pilot).
Question: Does Home help a nontechnical website owner make a correct decision and produce a usable developer handoff, enough to justify account, consent, recovery and time costs versus a normal browser?

## Participants and conditions
Recruit 12 consenting adults who actually manage, own or commission a website, are not implementation-team members, and have not used this candidate. Pilot, not statistical proof or population inference. No contacting people or public recruitment from this repository. Independent observer approves protocol, verifies eligible distinct humans/consent privately and assigns P01–P12 opaque tokens before starting. No names, contacts, passwords, recovery codes or private site URLs in GitHub. No recording without separate consent. Participants may stop at any time. Retain only authorized anonymized aggregate results in GitHub; keep private source evidence with observer under explicit retention/deletion policy. Do not replace dropouts after assignment or silently exclude failures. Participants who withdraw consent must not have individual records retained; report the aggregate withdrawal count, and do not treat missing evidence as success.

Each participant does both arms, 2 matched cases per arm. Preassigned 4-cell counterbalance, repeated 3 times; shuffle participant assignment before exposure, freeze it:
- cell 0: Browser first with set A, LUCH second with set B.
- cell 1: LUCH first with set A, Browser second with set B.
- cell 2: Browser first with set B, LUCH second with set A.
- cell 3: LUCH first with set B, Browser second with set A.
A: example.com (normal homepage), iana.org (redirect). B: example.org (normal homepage), wikipedia.org (redirect). These are public practice tasks, not actual customer outages. On each trial day the observer checks actual root HTTPS response and final browser URL separately; if a case no longer matches its category, pause before exposure, revise prospectively, never silently swap after seeing results. A normal browser may follow redirects; that is a legitimate advantage. Browser arm can use familiar standard browser tools including DevTools and notes; do not artificially restrict it. No external AI in either arm. No live production accounts or protected pages. No action that writes to a target site.

## Neutral facilitator instructions (read verbatim)
You are responsible for a website. A colleague asks whether visitors can reach the intended homepage and what should be done next. Using the assigned tool, investigate the two addresses, explain what you know and don't know, and prepare a short message to a developer. You may use normal browser functions in the browser condition and the provided workspace in the LUCH condition. Do not send a message to anyone or change a website. You can stop if you would not normally continue. Tell us when you are done.
Do not reveal expected HTTP statuses, ideal actions, rubric or the hypothesis that LUCH should win. Do not coach. If the participant asks for assistance, record it and use neutral clarification only. Ask for confidence (0–100), then ask whether and why the person would use this tool again. Preference only after both arms.

## Execution
Use separate fresh browser contexts. Start stopwatch before first instruction to open the assigned tool; include LUCH signup, recovery confirmation and scoped consent; never preregister an account. Arm time includes both cases and handoff. Stop after 12 minutes, mark unfinished as incomplete, record abandonment. Baseline permits normal address-bar navigation, inspect network if desired, and composing a message locally. LUCH uses genuine candidate UI and backend on private staging, actual public HTTPS requests, no mocked response. Observer retains exact observed sources, times, HTTP/redirect chain if available, and participant's own report; do not require DevTools or numeric HTTP if browser evidence supports the conclusion. Different observations from browser and LUCH may both be valid; evaluate against each tool's actual observation. No hints from synthetic fixtures. Do not score setup smoke as human work.
Use the first target then the redirect target in each set, record each separately. For both arms, ask for the next useful action and report; LUCH users may use its report, baseline users write their own. For repeat checks/history/revoke, record separately as LUCH-only usability outcomes, not a comparative primary success advantage. A blinded developer grades debranded, redacted handoffs in randomized order; remove formatting/branding clues without altering substance. Record observer and grader independence and private evidence references before scoring. No reports sent externally.

## Scoring
Each of the two cases has three binary items, graded against the actual observations:
1. Correct description of what the tool actually observed (normal homepage response or redirect/final destination as observed).
2. Correct limitation: no unsupported claim of overall uptime, payment, mobile, security or root cause; no assertion that a redirect necessarily means outage.
3. Specific reasonable next action for the owner/customer journey, grounded in observation, no bypass of access controls.
Blinded developer scores each report: correct target/source; observation/time sufficiently specific; no unsupported assertion; concrete actionable request. Full case success = all 3 case items and all 4 report items. Full arm success = both cases successful, no critical misconception, no substantive facilitator help, completed within 720 seconds. Missing/abandoned arm is not successful. Observer should score serious false assurance or outage claim as critical even if other items pass. Distinguish failure, partial, withdrawal and missing.
Primary measures: full-arm successes for LUCH and Browser on same participants; paired wins/losses; critical misconceptions; elapsed time including setup; preference after both arms. Secondary: help, abandonment, confidence, grader comments, LUCH history/revoke success. Record actual business impact separately in subsequent opt-in real-site task sessions; practice-case pilot alone does not establish commercial demand or actual repairs.

## Proposed pilot decision (must be independently approved before first participant)
- 12 assigned and all 12 complete both arms with valid retained consent/evidence for a positive pilot decision; otherwise inconclusive (never discard failed attempts).
- LUCH full-arm successes >=9/12, paired net full-success advantage >=3, no LUCH critical misconceptions, at least 8/12 prefer LUCH, median LUCH elapsed <= 1.25 times Browser median (same paired cohort; include setup).
- If valid completed cohort fails a threshold: REWORK, not another feature automatically. If both tools are similarly successful, examine signup friction or select a more valuable job; no automatic expansion.
- Even meeting criteria is only a promising pilot signal. Require independent verification of actual people and evidence, then genuine real-site tasks with consent, external usability/quality acceptance and release authority. No PRODUCT_READY from the scorer; no statistical significance claim.
The proposed thresholds and 12-participant design are HEA decisions, not Founder-approved or independently frozen. Independent observer must approve or revise and hash the protocol, assignment, rubric and candidate BEFORE recruitment/exposure. No threshold changes after observing data. A protected source registrar and independent signed receipts under PR #4151 are separate unfinished operational gates.
